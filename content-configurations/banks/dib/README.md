# DIB: the bank's configuration for WPS

DIB's real configuration, mined from the TransactHub source (the `PaymentHub` repository this runtime converges, plan W6). It lives here by the owner's decision of 2026-11-21, which amends D5 for DIB (`docs/runtime/NSTAR-CONVERGENCE-PLAN.md` section 8). Its values are real. Its tests use synthetic files only.

Shared content names no bank. The tenant id `dib` is in `spec/tools/deny-names.txt`, so check L09 refuses it in shared content, and `runtime/tests/TransactHub.Store.Tests/BankConfigurationTests.cs` refuses a bank's name in shared code.

| `core-banking.yaml` | port-bindings | `p.port.core-banking.v1` bound to the `gateway-rest` adapter, with the bank's settings. | The runtime (`PortBindings`) |

| `hooks/` | hook | The employer AML check and the labour ministry notification. | The studio |
| `activities/`, `ports/`, `simulators/` | activity, port, simulator | What the hooks call, and the test doubles for their ports. | The studio |
| `rules/` | | Empty. The bank has no rule of its own: its values set factory rules' parameters (below). | |
| `tests/` | test | Seven bank tests and one synthetic payment file (`tests/samples/`). | The studio |

Load it in the studio with `--bank dib` on any command, or `TH_BANKS=dib` for the server:

```
cd studio && npm run studio -- --bank dib check
cd studio && npm run studio -- --bank dib test
```

## What became what, and why

- **Rule values.** A value the factory already declares a parameter for is a value in `configuration-set.yaml`: the rails and the routing code. The routing code also decides `uae.wps.rule.agent-is-this-bank.v1`, so a payment file addressed to another bank's code is refused (BANK-RTE-002 to 004).
- **CBX values.** The source's CBX parameters keep their names, so the bank's existing values carry over. `BankRoutingCode` replaces the source's `DIBRoutingCode`.
- **Port binding.** Core banking is a port. The source's `CoreBanking:*` settings are the binding's settings, and switching core banking is a new binding with a later `validFrom`.
- **Hooks.** The source's two bank-only WPS steps with a business effect are hooks: the employer AML check (halt, after the file's checks, fails closed as the source did) and the labour ministry notification (notify, on close, fails open as the source did). Their services are bank ports, with simulators for tests.
- **Not bound.** No live salary-file workflow of the source calls either step: `dsl/workflows/dib-wps-outward.v1.workflow.json` (3.7.2), `dib-wps-outward-cbx.v1.workflow.json` (1.1.8) and `dib-wps-ui-upload.v1.workflow.json` (3.6.0) call only platform `wps.*` activities. Only a unit test calls them. Binding them would add steps the bank does not run today, so `bindings` is empty. To bind one, add a line:

  ```yaml
  bindings:
    - hookPoint: p.seg.check-and-screen.v1#after-validate
      hook: b.hook.employer-aml-check.v1
      release: 1.0.0
      validFrom: "<from when>"
    - hookPoint: p.wf.corporate.v1#on-close
      hook: b.hook.labour-ministry-notify.v1
      release: 1.0.0
      validFrom: "<from when>"
  ```

  `studio/test/bank-packs.test.ts` checks that these bindings are accepted.
- **Gone.** The source's queue pins (`wps-dib-platform`, `wps-dib-bank`), its default tenant and its bank routing rules (`WPS-DIB-OUTWARD-CHANNEL-IB-SIF-V1`, `WPS-DIB-OUTWARD-CBX-SIF-V1`) are not configuration. The factory's dispatch table chooses the workflow, and a tenant is always given.

## What a deployment must set

- `baseUrl` of the core-banking binding. It is `https://core-banking.dib.invalid/` here; the source's `HttpClients:CoreBanking:BaseUrl` is an internal host and is not carried.
- `TH_DIB_CORE_BANKING_TOKEN`.
- Where the AML screening and labour ministry services are, if their hooks are bound.
- Every value under "Not yet carried" that the deployment still needs, in the runtime's settings until a factory parameter or a port takes it.

## Privacy

No personal data is here. The tests' employer id, person ids and IBANs are the factory's synthetic values. The source's corporate records, names and accounts were not read into this folder. The maker and checker in `configuration-set.yaml` are role placeholders, not people.
