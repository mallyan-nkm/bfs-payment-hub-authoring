# DIB: the bank's configuration for WPS

DIB's real configuration, mined from the TransactHub source (the `PaymentHub` repository this runtime converges, plan W6). It lives here by the owner's decision of 2026-11-21, which amends D5 for DIB (`docs/runtime/NSTAR-CONVERGENCE-PLAN.md` section 8). Its values are real. Its tests use synthetic files only.

Shared content names no bank. The tenant id `dib` is in `spec/tools/deny-names.txt`, so check L09 refuses it in shared content, and `runtime/tests/TransactHub.Store.Tests/BankConfigurationTests.cs` refuses a bank's name in shared code.

## What became what, and why

- **Rule values.** A value the factory already declares a parameter for is a value in `configuration-set.yaml`: the rails and the routing code. The routing code also decides `uae.wps.rule.agent-is-this-bank.v1`, so a payment file addressed to another bank's code is refused (BANK-RTE-002 to 004).
- **CBX values.** The source's CBX parameters keep their names, so the bank's existing values carry over. `BankRoutingCode` replaces the source's `DIBRoutingCode`.
- **Port binding.** Core banking is a port. The source's `CoreBanking:*` settings are the binding's settings, and switching core banking is a new binding with a later `validFrom`.
- **Hooks.** The source's two bank-only WPS steps with a business effect are hooks: the employer AML check (halt, after the file's checks, fails closed as the source did) and the labour ministry notification (notify, on close, fails open as the source did). Their services are bank ports, with simulators for tests.
- **Built, but switched off.** No live salary-file workflow of the source calls either step: `dsl/workflows/dib-wps-outward.v1.workflow.json` (3.7.2), `dib-wps-outward-cbx.v1.workflow.json` (1.1.8) and `dib-wps-ui-upload.v1.workflow.json` (3.6.0) call only platform `wps.*` activities. Only a unit test calls them. Binding them would add steps the bank does not run today, so the shipped `bindings` is empty. Each hook is complete: the hook, the activity it calls and its script-behind (`scripts/`), the bank port, a simulator for the port, and tests (BANK-AML-001, BANK-AML-002, BANK-NTF-001 run each hook alone). `studio/test/dib-hooks.test.ts` binds both in a configuration that exists only in the test and runs a synthetic salary file end to end: the AML service clears the employer and the ministry is told; the AML service refuses the employer and nothing is sent to WPS; the ministry refuses and the payment still settles. The same file fails if either hook is bound in the shipped `configuration-set.yaml`.

  **To switch them on.** It is the bank's decision, made through maker-checker like any change to its configuration:

  1. Confirm the bank's AML screening and labour ministry services are reachable from the runtime, and set where they are at deployment (below, "What a deployment must set").
  2. Add the bindings to `configuration-set.yaml`, from the day they start:

     ```yaml
     bindings:
       - hookPoint: p.seg.check-and-screen.v1#after-validate
         hook: b.hook.employer-aml-check.v1
         release: 1.0.0
         validFrom: "<from when>"
       - hookPoint: p.wf.corporate.v1#on-close
         hook: b.hook.labour-ministry-notify.v1
         release: 1.0.0
         validFrom: "<from when>"
     ```

     One line switches on one hook; they are independent. A payment in flight keeps the bindings it started with (CK-PIN-02).
  3. In the same change, change the first case of `studio/test/dib-hooks.test.ts` ("ships with neither hook bound") to expect the bindings, and say why in the change.
  4. Run `cd studio && npm run studio -- --bank dib check`, `npm run studio -- --bank dib test` and `npx vitest run test/bank-packs.test.ts test/dib-hooks.test.ts`, then `npm run studio -- bank-pack dib --write` if an artefact changed.

  To switch one off again, give its binding a `validTo`; never delete a binding a payment may have started with.
- **Gone.** The source's queue pins (`wps-dib-platform`, `wps-dib-bank`), its default tenant and its bank routing rules (`WPS-DIB-OUTWARD-CHANNEL-IB-SIF-V1`, `WPS-DIB-OUTWARD-CBX-SIF-V1`) are not configuration. The factory's dispatch table chooses the workflow, and a tenant is always given.

## Posting by file

The source posted the agent's credits to core banking as a bulk file (its DE: generate the file, transfer it by SFTP, submit the upload, read the upload status, repost the failed lines). Here that is a connection, not a workflow step (Issue I-82, R-12-15): the runtime's `file-bulk` adapter of `p.port.core-banking.v1`. The bank chooses it by a new binding in `core-banking.yaml` with a later `validFrom`; no workflow changes, and the binding in force at the engine's time is the one a posting uses. The bank does not post by file here yet, so the binding is not added. Its settings:

```yaml
  - port: p.port.core-banking.v1
    adapter: file-bulk
    validFrom: <from when>
    settings:
      upload: gateway-rest            # the upload and its status over the bank's gateway; simulator in tests
      folder: <core banking's DE landing folder on p.port.file-transfer.v1>
      headerBranch: "997"              # the file's header (the source's DeBulkFile header branch, source code, description)
      sourceCode: <DeSourceCode>
      batchDescription: <DeBatchDescription>
      baseUrl: https://core-banking.dib.invalid/
      uploadPath: <the DE upload route>
      statusPath: <the getDeuploadStatus route>
      uploadFunctionId: <DeFunctionId>
      statusFunctionId: <the status query's function id>
      uploadUser: <WPSFlexCubeUser>
      uploadBranch: "997"
      externalHostId: IBMK
      statusPolls: "8"                 # the source's DetermineDeOutcome retry policy: 8 reads
      statusPollSeconds: "30"
      repostAttempts: "1"
      repostCodes: <CbRepostAutoRetryCodes>
      secretRef: env:TH_DIB_CORE_BANKING_TOKEN
      # and the balance settings of the gateway-rest binding, which the adapter's balance enquiry uses
```

The source's DE parameters (`DeSourceCode`, `DeBatchDescription`, `DeFunctionId`, `WPSFlexCubeUser`, `CbRepostAutoRetryCodes`) are seeded by no migration of the source, so no value is carried. The file goes through the bank's file-transfer binding, whose `sftp` adapter the runtime does not build yet (Issue I-129).

## What a deployment must set

- `baseUrl` of the core-banking binding. It is `https://core-banking.dib.invalid/` here; the source's `HttpClients:CoreBanking:BaseUrl` is an internal host and is not carried.
- `TH_DIB_CORE_BANKING_TOKEN`, `TH_DIB_SFTP_CREDENTIAL`, `TH_DIB_GPG_PASSPHRASE`, `TH_DIB_GPG_KEYS_PATH` and `TH_DIB_CB_WPS_PUBLIC_KEY` (the Central Bank's OpenPGP public key).
- The hosts of `file-transfer.yaml` (`centralBank.host`, `pickup.host`): `.invalid` placeholders here; the source names gateway profiles, not hosts.
- The accounting template's accounts (`settlementAccount`, `suspenseAccount`, `chargeIncomeAccount`, `vatAccount`) and any charge slab: not in the source (Issue I-58).
- Where the AML screening and labour ministry services are, if their hooks are bound, and where the labour ministry's establishment register is (`statusPath` and the host of `labour-ministry.yaml`, `TH_DIB_LABOUR_REGISTER_TOKEN`).
- Every value under "Not yet carried" that the deployment still needs, in the runtime's settings until a factory parameter or a port takes it.

## Privacy

No personal data is here. The tests' employer id, person ids and IBANs are the factory's synthetic values. The source's corporate records, names and accounts were not read into this folder. The maker and checker in `configuration-set.yaml` are role placeholders, not people.
