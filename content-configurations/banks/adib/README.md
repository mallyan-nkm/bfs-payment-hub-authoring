# ADIB: the bank's configuration (platform only)

ADIB's configuration, mined from the TransactHub source (the `PaymentHub` repository this runtime converges, plan W6). It lives here by the owner's decision of 2026-11-22, which amends D5 for ADIB, ENBD and FAB as it did for DIB on 2026-11-21 (`docs/runtime/NSTAR-CONVERGENCE-PLAN.md` section 8). Its values are the source's. Its tests use synthetic payments only.

Shared content names no bank. The tenant id `adib` is in `spec/tools/deny-names.txt`, so check L09 refuses it in shared content, and `runtime/tests/TransactHub.Store.Tests/BankConfigurationTests.cs` refuses the bank's name in shared code (`ADIB`, `Adib`, the full name).

## ADIB does not run WPS in the source

The factory has one scheme, WPS (`uae.wps`), and the platform. ADIB's deployment in the source runs IPI and FTS only:

- Its customer overlay, `infra/docker/docker-compose.customer-adib.yml` (and `docker-compose.customer-adib-hybrid.yml`), says "Licensed Rails: IPI, FTS" and sets `LICENSE_RAILS=ipi,fts` and `Worker__EnabledRails` `ipi`, `fts` on both workers.
- Its bank worker is built with `ENABLED_RAILS: "ipi,fts"` and `BANK_ID: "Adib"`. The worker's Dockerfile (`services/core/workers/PaymentHub.Worker.Shell/Dockerfile`) publishes a bank's WPS plugin only when `wps` is among its rails, so `PaymentHub.Activities.Bank.Adib.Wps` is never in ADIB's worker.

The source also has WPS parts that point at ADIB, but none of them runs: the base database seed (`infra/docker/mssql/init.sql`) subscribes the `adib` tenant to IPI, WPS and FTS; two generic WPS workflows run ADIB's WPS steps (`dsl/workflows/wps-outward.v2.workflow.json` 2.0.0, which calls the activity names only `AdibWpsActivities` serves, and `wps-salary-outbound.workflow.json` 1.0.8, whose bank steps are pinned to the queue `wps-adib`); and two Smart Integration templates carry `tenantId: ADIB` (`services/ecosystem/SmartIntegration/PaymentHub.SmartIntegration.API/templates/wps-sif-upload.request.json`, `wps-sif-reference.request.json`). No worker of ADIB's deployment serves `wps-adib` or loads the WPS plugin. The source contradicts itself on whether ADIB is meant to run WPS (Issue I-86); this folder follows what it deploys and configures the platform only.

## What became what, and why

- **Rail values.** The factory declares one rail parameter, and the bank runs none of the factory's rails, so the value is the empty list. It is the factory's default; it is set here so that the bank's choice is on record with its source. BANK-RAIL-001 shows a payment that asks for WPS finds no rail; `studio/test/platform-bank-packs.test.ts` runs a salary file through `p.wf.corporate.v1` for the bank and it is refused at routing, before anything is sent.
- **No routing code.** The source has no WPS routing code for ADIB (the WPS parameter migrations seed only DIB's), so `uae.wps.rule.agent-is-this-bank.v1#ownRoutingCodes` keeps the factory default, none. BANK-RTE-001 shows that a payment file addressed to a routing code is then not this bank's.
- **Port binding.** Core banking is a port. The source holds no gateway setting of the bank's, so the binding carries the host as a `.invalid` placeholder and the credential by reference, and nothing else. The runtime's adapter refuses every call with "has no '...'" until the bank's settings are added, so no payment of the bank posts to a simulator or to a guessed host (Issue I-85, `PlatformOnlyBankFolderTests`). The bank's settings come as a new binding with a later `validFrom`, as DIB's did.
- **Hooks.** The bank's two WPS steps with a business effect are hooks, as DIB's are: the employer AML check (halt, after the file's checks, fails closed as the source did) and the labour ministry notification (notify, on close, fails open as the source did). Their services are bank ports, with simulators for tests.
- **Built, but switched off.** No live workflow of ADIB calls either step. `AdibWpsEmployerAmlCheck` is called by no workflow. `MohreNotification` is called by `dsl/workflows/wps-outward.v2.workflow.json` (steps `mohre_salary_notification`, `mohre_salary_completion`, `mohre_refund_notification`, `mohre_nak_notification`) and `wps-rtc.sub-workflow.json` (`mohre_refund_notify`), but ADIB's worker does not load the WPS plugin that serves it, and ADIB runs no WPS workflow. So the shipped `bindings` is empty. Each hook is complete: the hook, its activity and script-behind, the bank port, a simulator, and tests (BANK-AML-001, BANK-AML-002 and BANK-NTF-001 run each hook alone). `studio/test/platform-bank-packs.test.ts` binds both, with WPS switched on, in a configuration that exists only in the test, and runs a synthetic salary file end to end: the employer cleared and the ministry told; the employer refused and nothing sent; the ministry refusing and the file still settled. The same file fails if either hook is bound in the shipped `configuration-set.yaml`.

  **To switch them on.** It is the bank's decision, made through maker-checker like any change to its configuration, and it needs WPS first: the rail (`p.table.rail-choice.v1#enabledRails` = `[uae.wps]`), the bank's routing code, its core-banking settings and its WPS bindings, which the source does not hold (below). Then add the bindings to `configuration-set.yaml`, from the day they start:

  ```yaml
  bindings:
    - hookPoint: p.seg.check-and-screen.v1#after-validate
      hook: b.hook.employer-aml-check.v1
      release: 1.0.0
      validFrom: "<from when>"
    - hookPoint: p.wf.corporate.v1#on-close
      hook: b.hook.labour-ministry-notify.v1
      release: 1.0.0
      validFrom: "<from when>"
  ```

  One line switches on one hook. In the same change, change the case "ships with neither hook bound and no rail" of `studio/test/platform-bank-packs.test.ts` and say why. Run `cd studio && npm run studio -- --bank adib check`, `npm run studio -- --bank adib test` and `npx vitest run test/platform-bank-packs.test.ts`, then `npm run studio -- --bank adib bank-pack adib --write` if an artefact changed. To switch one off again, give its binding a `validTo`.
- **No bank rule.** `AdibValidateWpsRules` (at least one record, total within the balance, an employer the labour ministry has suspended is refused) is the same code in each bank's fork. The plan makes it one `uae.wps` rule, not a bank rule; the factory has the first two (`uae.wps.rule.record-count-matches.v1`, `p.reserve.funds.v1`) and not the third (Issue I-88).
- **Gone.** The queue pin `wps-adib` and the per-bank queue routing are not configuration: the factory's dispatch table chooses the workflow, and a tenant is always given.

## What a deployment must set

- The bank's core-banking settings, as a new binding of `p.port.core-banking.v1` with a later `validFrom`: `baseUrl` (a `.invalid` placeholder here), `balancePath`, `postingPath`, `balanceFunctionId`, `postingFunctionId`, `serviceCode`, `externalHostId`, `txnFlag`, `uploadBranch`, `balanceFlag`, `authStatus`, and `referencePrefix` if the bank has one (I-85).
- `TH_ADIB_CORE_BANKING_TOKEN`.
- Where the AML screening and labour ministry services are, if their hooks are bound.

## Privacy

No personal data is here. The tests' payments, accounts and routing codes are synthetic (the factory's sample values). The source's records and names were not read into this folder. The maker and checker in `configuration-set.yaml` are role placeholders, not people.
