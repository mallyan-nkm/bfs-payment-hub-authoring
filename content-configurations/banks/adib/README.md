# ADIB: the bank's configuration for WPS

ADIB's configuration, mined from the TransactHub source (the `PaymentHub` repository this runtime converges, plan W6). It lives here by the owner's decision of 2026-11-22, which amends D5 for ADIB, ENBD and FAB as it did for DIB on 2026-11-21 (`docs/runtime/NSTAR-CONVERGENCE-PLAN.md` section 8). Its values are the source's. Its tests use synthetic payments only.

Shared content names no bank. The tenant id `adib` is in `spec/tools/deny-names.txt`, so check L09 refuses it in shared content, and `runtime/tests/TransactHub.Store.Tests/BankConfigurationTests.cs` refuses the bank's name in shared code (`ADIB`, `Adib`, the full name).

## ADIB runs WPS

The source contradicts itself on whether ADIB runs WPS (Issue I-86): its customer overlay licenses IPI and FTS only (`infra/docker/docker-compose.customer-adib.yml`, `LICENSE_RAILS=ipi,fts`) and its bank worker is built without its WPS plugin; but the base database seed subscribes the `adib` tenant to WPS (`infra/docker/mssql/init.sql`, `TenantSubscriptions`), the WPS outward workflow `dsl/workflows/wps-outward.v2.workflow.json` (2.0.0) calls the activity names only the bank's WPS plugin serves (`services/activities/bank/Adib/PaymentHub.Activities.Bank.Adib.Wps/AdibWpsActivities.cs`), and `wps-salary-outbound.workflow.json` (1.0.8) pins its bank steps to the queue `wps-adib`. The owner decided on 2026-11-22 that ADIB runs WPS on this platform. This folder therefore carries the WPS values the source holds for the bank, and says which it does not hold.

## What became what, and why

- **Rail values.** The bank runs WPS, so the rail is `[uae.wps]`. BANK-RAIL-001 shows a salary payment is routed to WPS.
- **No routing code.** The source has no WPS routing code for the bank (the WPS parameter migrations seed only DIB's), so `uae.wps.rule.agent-is-this-bank.v1#ownRoutingCodes` keeps the factory default, none: a payment file addressed to a routing code is not this bank's (BANK-RTE-001) until the bank gives its code (I-116).
- **Port bindings.** Core banking, file transfer and encryption are ports. Core banking keeps the placeholder binding of I-85: the runtime's adapter refuses every call until the bank's settings are added. The file transfer carries the folders of the bank's WPS plugin; the hosts are `.invalid` placeholders, as the source reaches them through its SFTP gateway. The encryption binding names the Central Bank's public key by reference.
- **Hooks, by DIB's rule.** A hook is built for each of the bank's WPS steps with a business effect, and bound only when a live flow of the bank calls the step. `wps-outward.v2` calls the labour ministry notification, so it is bound on close (fails open, as the source's did). No workflow calls the employer AML check, so it stays unbound; binding it is a line in `configuration-set.yaml` with its `validFrom`:

  ```yaml
  - hookPoint: p.seg.check-and-screen.v1#after-validate
    hook: b.hook.employer-aml-check.v1
    release: 1.0.0
    validFrom: "<from when>"
  ```

  In the same change, change the case "binds the labour ministry notification its WPS workflow calls" of `studio/test/adib-wps.test.ts` and say why. Run `cd studio && npm run studio -- --bank adib check`, `npm run studio -- --bank adib test` and `npx vitest run test/adib-wps.test.ts`, then `npm run studio -- --bank adib bank-pack adib --write` if an artefact changed. To switch a hook off again, give its binding a `validTo`.
- **The suspended employer is the scheme's rule.** `AdibValidateWpsRules` (at least one record, total within the balance, an employer the labour ministry has suspended refused) is the same code in each bank's fork; the factory has all three as `uae.wps` content (`uae.wps.rule.record-count-matches.v1`, `p.reserve.funds.v1`, `uae.wps.rule.employer-not-suspended.v1`). BANK-WPS-002 shows a suspended employer's file refused for the bank, nothing sent.
- **Gone.** The queue pin `wps-adib` and the per-bank queue routing are not configuration: the factory's dispatch table chooses the workflow, and a tenant is always given.

## What a deployment must set

- The bank's core-banking settings, as a new binding of `p.port.core-banking.v1` with a later `validFrom` (I-85).
- The hosts of `file-transfer.yaml` (`centralBank.host`, `pickup.host`), `.invalid` placeholders here.
- `TH_ADIB_CORE_BANKING_TOKEN`, `TH_ADIB_SFTP_CREDENTIAL` and `TH_ADIB_CB_WPS_PUBLIC_KEY` (the Central Bank's OpenPGP public key, armoured or binary).
- The bank's WPS routing code and its CBX values, once it gives them (I-116), and confirmation that the four general-ledger names are its accounts.
- Where the AML screening and labour ministry services are; where the labour ministry's establishment register is reached (I-118).

## Privacy

No personal data is here. The tests' payments, accounts and routing codes are synthetic (the factory's sample values). The source's records and names were not read into this folder. The maker and checker in `configuration-set.yaml` are role placeholders, not people.
