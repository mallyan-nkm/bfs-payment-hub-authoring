# CLAUDE.md

Guard-rails for work in this repository. Normative words follow RFC 2119. Read this file first, every session.

## What this repository is

The specification of the TransactHub Designer Studio: the design-time tool in which a payments workflow designer defines, tests and exports payment workflows. It holds the design spec, the schemas, a factory pack of default content, a conformance kit, and a build backlog whose stories are prompts for you.

The studio is a design-time tool. It MUST NOT read or change a running payment.

## How to work a story

1. Take one story from `build/Cnn-*.md`. Its `Done first` list MUST be complete.
2. Read what its Definition of Ready names. Read nothing into the spec that is not there.
3. Start in plan mode. The plan lists the files to add or change, the tests you will write first, and the evidence you will show for the Definition of Success. Write no code until the plan is accepted.
4. Work on the story's branch. One story, one branch, one pull request.
5. Write the tests first and see them fail.
6. Stay inside the story. What you find outside it goes in the pull request under "Found, not fixed".
7. Stop when the Definition of Done holds and the Definition of Success is shown with evidence.

If the spec is wrong, silent or contradicts itself: stop. Write it up as an Issue and a Recommendation. Do not invent an answer and build on it. A change to the spec goes in the same pull request as the code that needs it, with a requirement id and a check.

## Guard-rails

### Names and scopes

- A name is `<scope>.<type>.<name>.v<major>`. Scopes are `p`, `<cluster>.p`, `<cluster>.<scheme>` and `b`. Never write `platform.`.
- A scheme MAY depend on its cluster platform and on `p`. A cluster platform MAY depend on `p`. `p` depends on nothing. Shared content MUST NOT depend on `b`.
- A tenant id MUST NOT appear in a name. It lives in the pack manifest.
- Shared content MUST NOT name a bank or a vendor. Add every tenant id and vendor product name to `tools/deny-names.txt`.

### Versions

- The major is in the name. A release is `major.minor.patch`: an interface change is a major, an improvement is a minor, a fix is a patch.
- A published release MUST NOT be edited. Release a new one.
- Pins are exact: name, release and hash. Never write a range.
- Values, lists and registries are looked up by date and reach payments in flight. Logic is pinned and does not. Do not blur the two.

### The DSL

- The keys `on`, `off`, `yes` and `no` MUST NOT be used; YAML reads them as booleans. Use `handle` on a call or a slot and `by` on a switch.
- Every non-primary outcome MUST be handled. Nothing else may be.
- A workflow holds flow only. Rule evaluation and lookups run in activities.
- A value a bank may change is a parameter with a default and bounds. It is never a constant.
- A handler holds no state: no await, timer, hold or write.
- An `await` and a `return` appear only in a subflow. A designer's workflow calls a composite activity as one step; the wait is in its subflow.
- A `block` appears only in the expanded form. Engines and the interpreter run the expanded form; nobody edits it.
- Retry is allowed only on an activity that is pure, read, or carries an idempotency key.

### Data

- The context is the canonical ISO 20022 model. Only map blocks touch another format.
- There is no untyped field. A scheme or bank field is a registered extension.
- Personal data MUST NOT appear in workflow state, logs, tests, samples, prompts or commit messages. Use references and synthetic values.

### Scripts-behind and simulators

- A script uses only the injected interface: `ctx`, `ports`, `rules`, `params`, `clock`, `ids`, `log`. No network, file system, system clock, randomness or environment.
- A simulator MUST NOT be part of a promotable pack.
- The studio offers functional tests only. Do not add load, back-pressure or soak tests.

### Generated files

A file whose first line says `Generated by` MUST NOT be edited by hand.

| Generated | Edit instead |
| --- | --- |
| Factory activities, rules, rule sets, tables, ports, simulators, extensions and tests | `tools/build_factory.py` |
| `pack.yaml` in each pack, `factory/inventory.yaml` | `tools/build_factory.py` |
| `build/00-backlog.md`, `build/Cnn-*.md` | `build/backlog/*.yaml` |
| `expanded/*.yaml` | The authored workflow or the subflow; then `tools/expand.py` |
| Blocks between `<!-- NAME -->` and `<!-- /NAME -->` in `design/` and the READMEs | `tools/build_docs.py` |

Workflows, scheme manifests, the example bank's hooks and configuration set, the engine bindings, the supersession example and the conformance kit are written by hand.

### Checks

- Mechanisms over assertions. A rule in the spec names the check that enforces it.
- A new check goes into three places in one change: the catalogue in `design/05-workflow-dsl.md`, the validator, and a case in `tools/mutation_tests.py` that breaks the repository and expects the check to fire.
- Never weaken a check to make content pass. Fix the content, or raise an Issue and a Recommendation.

## Commands

```
pip install -r tools/requirements.txt
python3 tools/build_factory.py     # regenerate the generated factory artefacts, manifests and inventory
python3 tools/validate.py          # schemas and static checks; exit 1 on any error
python3 tools/expand.py            # write the expanded form of every workflow that calls a composite
python3 tools/mutation_tests.py    # break the pack once per check; every case must be caught
python3 tools/build_docs.py        # check the backlog; render build specs and generated blocks
```

Run all five, in that order, before you open a pull request. `python3 tools/expand.py --check` fails when `expanded/` is out of date.

## Common Definition of Done

Every story carries these lines as well as its own.

- Tests were written first, and all are green.
- `tools/validate.py` exits 0, `tools/expand.py --check` passes, `tools/mutation_tests.py` catches every case, `tools/build_docs.py` exits 0.
- No generated file was edited by hand.
- Every new requirement has an id and a check. Every new check has a mutation case.
- No bank name, no personal data and no secret is in the change.
- The pull request shows the evidence for the Definition of Success, and lists what was found and not fixed.
- The change is one story on one branch.

## Writing

- British English. Short sentences. Plain words.
- No em-dashes. Use a full stop, a comma or a colon.
- RFC 2119 words in capitals, only where a requirement is meant.
- A problem is written as an Issue and a Recommendation.
- A requirement is one row: id, requirement, check.

## Provisional content

`uae.wps` is provisional. It was written from public sources, not from the scheme rulebook. It is the only scheme in the factory. Treat every scheme fact in it as unconfirmed until `provenance.status` says `confirmed`. Do not present a provisional fact as a scheme rule in code, tests or messages to a user.
