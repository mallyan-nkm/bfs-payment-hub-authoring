1. Start here

The TransactHub Designer Studio is where a payments workflow designer defines, tests and exports payment workflows, built from blocks over one ISO 20022 canonical context. It is a design-time tool: it never reads or changes a running payment.

This guide has three paths through it. Take them in order the first time.

Path A, one hour

Set up and look around

Install and start the studio (part 2), read the ideas (part 3), then exercises 1 to 5 of the training path.

Path B, two hours

Learn every feature

Work through the rest of the training path, with the feature reference open beside it.

Path C, two hours

Build a full workflow

Build a new scheme, its leg and everything they need, approve it, enable it for a bank, pay a file end to end, then export and deploy it (part 6 and part 7).

2. Set up and run

The studio is a Node.js server with a web app. It reads its schemas and conformance kit from the specification repository beside it, and keeps everything else, your own work included, as files on a GitHub branch, read into memory. Nothing is kept on disk. Without .NET and Java, everything works except running on a real engine; install them when you reach part 7.

If the build fails with error NU1100: Unable to resolve 'Microsoft.Azure.DurableTask.Core', NuGet cannot reach a package source. The harness folder names nuget.org in its own nuget.config, so take the latest code with git pull. If it still fails, your network blocks api.nuget.org: on a company network, ask for your proxy settings or an internal NuGet mirror, and add the mirror with dotnet nuget add source <url> -n company.
On Windows, if the kit or a deploy says An Application Control policy has blocked this file (0x800711C7), Windows is refusing to load the harness the studio just built, because it is not signed. The cause is either Smart App Control (Windows 11, personal PCs) or an App Control or AppLocker policy set by your organisation. Event Viewer, under Applications and Services Logs, Microsoft, Windows, CodeIntegrity, Operational, names the policy. Ways forward:
  • A company PC: ask IT to allow the folders studio\engines\dtfx\harness\bin and studio\engines\elsa\harness\bin, or to give you a developer exception. Do not try to get round the policy.
  • Any PC with WSL: run the studio inside WSL (Ubuntu), where Linux programs are not subject to this policy. Install Node.js and the .NET 8 SDK inside WSL and follow the Linux steps of this guide.
  • A personal Windows 11 PC: in Windows Security, App and browser control, Smart App Control settings, choose Off. It cannot be turned back on without resetting Windows, so decide with care.
Everything else in the studio works without DTFx: the interpreter, the test bench, the kit on the studio and the export.

3. The ideas you need

Read this once. Come back to it when a step mentions a word you do not know; the glossary has the short versions.

Tenants, users and maker-checker

One studio serves several banks. Each bank is a tenant. The owner tenant holds shared content: the platform and the schemes. A bank reads shared content and never changes it; it sets its own configuration values and writes hooks. You sign in to the studio, with the studio's own identity provider (for local work and training, the built-in development sign-in lists the users). Everything you do is done as that user, in that user's tenant, and the server checks every change against one permission table. To act as another user, Sign out in the top bar and sign in as them. Each role lands on its own page and sees only the views its work needs in the left menu. The studio's sign-in is separate from the runtime's: a runtime token is never accepted.

Maker-checker. A maker's saves need no approval. A change set becomes a version, the thing that is exported, only when an approver for its area approves it, and the approver is never one of its makers. Every save, approval and refusal goes into a hash-chained audit log.

Names, scopes and releases

Every artefact name is <scope>.<type>.<name>.v<major>, for example uae.p.validate.iban.v1.

ScopeWhat it isExample
pThe platform, the same everywherep.wf.corporate.v1

A release is major.minor.patch. An interface change is a new major, which is a new name (.v2); an improvement is a minor; a fix is a patch. A published release never changes. A change is a new release, and the studio proposes which one from the interface difference.

Values and logic. A value a bank may change (a limit, a list of rails, a cut-off) is a parameter with a type, a default and bounds. The bank sets it in its configuration set with a validFrom and, if it ends, a validTo; a value outside its bounds, or two periods that overlap, is refused (L14). Values are looked up by date, so they reach payments already in flight. Logic is pinned when an instance starts and does not change under it.

Effects, attempts and idempotency keys

Every activity declares its effect: pure (only the context, its parameters and its rule sets), read (it reads outside state), write or external. Every attempt is at least once on every engine: an attempt in flight when its worker stops is run again (R-03-25). So an activity with an outside effect (a write or external effect, a reserve, hold or notify, an exchange that sends) carries an idempotency key built from a business id of the header, whether or not it retries (check L54). Retry is allowed only on an activity that is pure, reads, or carries a key.

A validate or decide with no rule sets is a check of its own. It is pure when it is bound to a script and names no port, and read otherwise (check L57, I-342). A pure activity never names a port; the interpreter refuses a port call from one.

How a payment runs

Learn this path. Most of the exercises follow it, and part 6 builds every piece of it.

flowchart LR
  F[File or message] --> D{Dispatch table}
  D -->|start: kind, direction, segment| I[Intake map]
  I --> S[workflow-select]
  S --> P[Platform workflow]
  P --> R[Route: enabled rails]
  R --> L[Scheme leg in the slot]
  L --> X[Post, verify, notify]
  D -->|deliver| A[Workflow that awaits it]
  1. A file or message arrives at the front door.
  2. The scheme's dispatch table says what it is. A start message names the payment it starts (kind, direction and, for an outward payment, segment), its intake map and the leg to start. The dispatch table routes; the intake map only reads the file. Check L33 makes sure every start message leads somewhere real.
  3. The intake map turns the file into the canonical context: header, batch, items.
  4. p.table.workflow-select.v1 picks the platform workflow from the kind, direction and segment. An outward corporate payment runs p.wf.corporate.v1.
  5. The platform workflow validates, screens, checks limits, reserves funds and routes. The route step passes only a rail the bank has enabled in its configuration.
  6. The platform workflow has a slot called scheme-leg. The leg the dispatch table named fills it and does the scheme's part.
  7. Back in the platform workflow: post, verify, notify, with the bank's hooks wherever it bound them.

Composites and the expanded form

A step that talks to a party and waits for an answer calls a composite activity. Underneath, a subflow sends, awaits and reads the reply. The designer sees one step; engines run the expanded form, where each composite step becomes a block of inner steps. A run shows two traces: the business trace, one line per authored step, and the detail, the inner steps.

  • submit:accepted
  • submit.send:accepted
  • submit.await-ack:received
  • submit.read-ack:ack

Runs, benches and the virtual clock

A run happens on a virtual clock that starts on the evaluation date. A wait of days ends at once, and a run is deterministic. A bench binds each port to a simulator and a scenario. A port left out of the bench uses its default simulator, and the run report says so.

Change sets

Some drafts refer to one another: a port and its simulator, a composite and its subflow, a scheme and its legs. None can be published first. Approving a draft therefore publishes its change set, which the studio generates: the draft and every draft it refers to or that refers to it. They are checked and tested together, and all publish or none does. Each change set gets an id such as CS-2026-11-17-001, and an export lists the change sets its artefacts came from.

What reaches the runtime

The studio never runs a payment. What it gives a bank's runtime is built on approval, signed with the studio's key, and published to the content branch, never rewritten:

  • A distribution: the logic one bank runs (the platform, the schemes it licenses and the bank's own pack), with the parameter contract of every dial. A platform or scheme approval builds one for every bank that takes it; a bank's own pack or licence approval builds that bank's.
  • A configuration release: the bank's values, its reference tables and its port bindings. Each approval that changes one gets a release of its own, numbered per approval: the configuration set's release, or the minor after the bank's newest. It is never a patch (I-340, R-11-115).

On the bank's runtime, a service engineer installs a distribution and puts a configuration release in force; neither happens until a person with the bank approver's role consents (R-09-77). Part 8 points to the runtime's own guides.

4. Every feature

A reference to every view in the left menu, then the command line and the HTTP API. Each view lists what it is for, its main controls, and something to try.

The frame of every page

Every screen is built with Microsoft Fluent UI 2 (docs/adr/0003-ui-fluent.md), the same as the runtime's consoles. A deep navy top bar holds the product name, a search box (Find an artefact by name or path, which opens the catalogue), a badge for the tenant you work for (shared content, or the bank's name), a design time badge, the theme menu (light, dark, or as the system; kept in your browser only), your initials, name and roles, and Sign out. The left menu lists, with an icon each, only the views your roles may use; at its foot is the number of documents you can see. On a narrow screen the menu folds behind the Menu button.

Choices within a page are Fluent tabs, not buttons: the editors' kinds, the test bench's Tests and Ad hoc bench, a run's input, the designer's Canvas, Outline and Expanded form, an artefact page's summary and its YAML, the tabs of governance. Click a tab to switch; the page does not reload. A message after an action (Saved draft …, Refused (403 …)) appears in a coloured bar near the button you pressed. The screenshots in docs/ui/screenshots/ show the main views, in light and dark.

The assistant beside every page

Beside the editors, the workflow designer, a bank's configuration and the test bench sits a panel with two tabs. Close it with ×; open it again with the Assistant tab on the right edge.

Import

Brings a scheme in from its source code. An AI coding agent, given the source and the extraction prompt (Download the extraction prompt on the page, or docs/import/EXTRACTION-PROMPT.md), writes an extraction bundle: the studio's own documents, scripts-behind, synthetic samples, tests, a bank's configuration, an inventory of every file and every unit of the source with where each went, and findings (differences between code and spec, questions, error scenarios). The agent checks its bundle with npm run studio -- import <bundle> until it reports no errors.

  • Choose a bundle zip, or Use the training bundle (the factory WPS scheme extracted as uae.wpsx). A platform user imports the shared part; a bank part (scope b, configuration sets) is left for that bank, whose configurator imports it once the shared part is a version.
  • Preview shows what the bundle holds; the coverage of the source (every file inventoried or excluded with a reason; a file in neither is an error); what was retired, sent to infrastructure, or left unmapped for the expert; the findings; every check (schemas, the static checks, no personal data, no bank name in shared content, scripts inside the injected interface, every document explained by the source, a changed published block given a new release); and the bundle's tests, run against the bundle itself before anything is saved.
  • Import as drafts, as … saves everything as drafts (an unchanged block is reused, not saved again), with provenance naming the source and its revision. Nothing is published: an approver approves each change set as a version in Governance. A user who may not author a document of the bundle is refused before anything is saved.

Test bench

Two tabs at the top. Tests lists every test the tenant can see, with its last result: Filter tests, then Run or Debug one, or Run all. A test saved but not yet approved carries a draft badge. Ad hoc bench runs anything you choose:

  • Under Ports and simulators, Add a port for each binding: Port, Simulator, Scenario. Under Signals, Add a signal for pause, resume, cancel or re-screen at a virtual time.
  • Under Input, two tabs: Context as JSON and Inbound sample. On Inbound sample, choose the sample; Add a sample file saves a new synthetic one. For a whole payment from the bank's channel, also choose the Start message.
  • Optionally write what you expect, under Expect (optional).
  • Tick Run with my drafts to run your tenant's drafts in place of their published releases: an activity and its script can be tried before anyone approves them (I-341). The report then says Draft run and names the drafts. A draft run publishes nothing and never counts as a test's result.
  • Run the bench, or Debug step by step.

The run report: the outcome, the virtual time and the clock's start; Warnings (each port the run reached that was not on the bench, and the simulator it used instead); Checks; Business trace; Detail, the steps inside composites. Then tabs: Release trace, Timeline (on the virtual clock, with Open every composite), Instances, Messages and Bench and bindings; below them the steps and context deltas, rule traces, and any duplicate or unmatched messages.

Save the run as a test. Under the report, Save the run as a test (assertions) fills a test from the run: Test id, Title, and ticks for the outcome, the reason code, the virtual time, the attempts per step, the business trace, the detail and the messages, each editable. The debugger

On the bench, Debug step by step runs the same thing end to end, on the studio's virtual clock, and opens the debugger instead of the report. A saved test has a Debug button beside Run. Nothing it does touches a running payment.

  • Where the run is, on the left: the workflow (and, inside it, the leg or hook it is in), and its steps. A shared segment shows its own steps. Each step is ticked with its outcome as the run reaches it, and the current one is outlined.
  • What happened, on the right, in plain words; then Decisions and rules (the decisions a step took, its findings with reason codes, the rules and tables that ran); Data changed by this event, before and after; and All the data now, with what changed marked.
  • Step into ▶ moves one event forward, into a leg or hook when the run goes there. Step over ⤼ moves on at the same level, past a leg or hook at one go. Step out ⤴ goes back up to the workflow that started this one. ◀ Step back and ⏮ Restart go backwards: a run is the same every time, so stepping back is exact.
  • Click the dot beside a step to set a breakpoint; Continue ⏭ runs to the next one, or to the end. Tick every event to stop on attempts, replies and the rest too. The whole run, event by event lists every stop; click one to jump there. Show the run report gives the usual report.
The debugger keeps the data after every event. For a very large batch it stops keeping it after a limit and says so; debug a smaller sample to see every step.

Conformance kit

Tenant

A bank's configuration set, for its Bank Configurator and Bank Approver. A saved configuration set is a draft until the Bank Approver approves it as a version in Governance; that approval builds the bank's next configuration release.

  • Configuration set (its release, the accepted shared releases, who approved it), Parameters and Hook points: what the bank has set and bound now.
  • Edit the configuration set: the Configuration set YAML, Reset, and Save the configuration set. The set is checked on every edit: a value outside its bounds or an overlapping period shows L14, and the save stays off until it is fixed. A changed set needs a later release, a minor or a major: a patch is refused (L53). Bump the release proposes the next minor.
  • Parameters this bank may set: every parameter with its default and bounds, and Set a value.
  • Compatibility run: before the bank accepts a new shared release, each bound hook point must still exist with a compatible contract and each of its hook tests must pass.
  • Tenant export: the shared packs the bank accepted, by hash, its bank pack and its configuration set.

Export

Builds the package an engine runs. Tick the Workflows (Filter workflows helps), and under Target and tenant choose the Target: temporal (the default), dtfx, flowable or elsa, and the Tenant. Optionally tick With simulators, for a test deployment; then Preview and Download the zip.

The manifest lists: the workers, one per task queue, each with the tasks it serves; the tasks, each named name@release; the flows in expanded form with their pins; the change sets the artefacts came from; and every file with its hash. Every package is signed: release.json states the release and the hash of every file, and release.sig is the studio's signature over it (R-09-23); a deploy refuses a package that does not verify. Flowable packages carry generated BPMN and a portability report. Temporal, DTFx and Elsa packages differ only in their binding: each runs the documents with one generic interpreter. A package with simulators is marked not promotable. The same request gives the same bytes.

// The demo credit file: one H record (file reference, debtor routing code, currency, count, total)
// and a D record per credit (IBAN, amount). The map reads the file; the dispatch table says what
// payment it starts (R-05-42).
export async function run({ ctx }) {
  const text = String(ctx.messages?.inbound?.payload ?? '');
  const ls = text.split(/\r?\n/).map((l) => l.trim()).filter((l) => l && !l.startsWith('#'));
  const h = ls.filter((l) => l.startsWith('H,'));
  const d = ls.filter((l) => l.startsWith('D,'));
  if (h.length !== 1 || d.length === 0) return { outcome: 'unmappable', reasonCode: 'FF01' };
  const [, fileRef, routing, currency, count, total] = h[0].split(',');
  ctx.header = { ...(ctx.header ?? {}), fileId: fileRef, endToEndId: fileRef };
  ctx.batch = { id: fileRef, numberOfTransactions: Number(count), controlSum: Number(total), currency, debtorAgent: { clearingMemberId: routing } };
  ctx.items = d.map((l) => {
    const [, iban, amount] = l.split(',');
    return { payment: { creditorAccount: { iban }, instructedAmount: { value: Number(amount), currency } } };
  });
  return 'mapped';
}

  3. Sign in as example.checker. In the Bank workspace, under Schemes licensed, click Approve the licence.
  4. Open Governance and click Approve as version on the config:example-bank row. Sign in as example.maker again.

7. Export, deploy and run

An export package is everything an engine needs, signed. The deploy runner checks the signature, then starts the package on the engine it was exported for (DTFx, Elsa, Temporal, or Flowable), the way production would run it: a separate worker process per task queue, each serving only its own tasks. It is a test of a package on one machine; a bank's runtime is part 8.

8. The runtime side

The studio designs and releases; the runtime runs payments. This guide stops at the studio's edge. Here is where to go next.

  • One bank per runtime. A runtime serves exactly one bank, set at install (TH_BANK), and refuses another bank's distribution, configuration release, payment or file (R-09-76). The studio stays multi-tenant.
  • What it takes from the studio. The signed distributions and configuration releases of part 3, which the service console installs from the studio's content branch. It verifies each signature before it stores a release and again before it activates one or puts it in force. A bank's values reach the runtime only in a signed configuration release, checked against the bounds of every distribution it has (R-09-110).
  • Consent. Every change of the system (installing a distribution, putting a configuration release in force, a register change, a troubleshooting action) is asked for by one person and done only when another person with the bank approver's role consents (R-09-77).
  • The consoles. The operations console is for operators and supervisors: payments, their timelines, work queues, holds, reports and the bank's registers. The service console is for service engineers: health, content install and activation, configuration releases, backups, the error and event log and its runbooks. Both are on Fluent UI 2, like the studio.
