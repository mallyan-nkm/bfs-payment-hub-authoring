1. Start here

The TransactHub Designer Studio is where a payments workflow designer defines, tests and exports payment workflows, built from blocks over one ISO 20022 canonical context. It is a design-time tool: it never reads or changes a running payment.

This guide has three paths through it. Take them in order the first time.

Path A, one hour

Set up and look around

Install and start the studio (part 2), read the ideas (part 3), then exercises 1 to 5 of the training path.

Path B, two hours

Learn every feature

Work through the rest of the training path, with the feature reference open beside it.

Path C, two hours

Build a full workflow

Build a new scheme, its leg and everything they need, approve it, enable it for a bank, pay a file end to end, then export and deploy it (part 6 and part 7).

Prefer to watch first? Two narrated demos, recorded from the studio itself, are in the repository: docs/demo/01-concepts-and-walkthrough.mp4 (about four minutes: the ideas and a tour) and docs/demo/02-build-a-scheme-from-scratch.mp4 (about five minutes: part 6, start to finish, ending with the deploy on DTFx). Each has an .srt subtitle file beside it. For a slower start, two training videos are in docs/demo/training/: training-1-the-ideas.mp4 (about ten minutes, no screens: every idea drawn as a restaurant kitchen) and training-2-hands-on.mp4 (one long file: a rule and its examples, an activity on the bench, the AI assistant's templates, a leg composed on the canvas, what to build when nothing exists, and a bank's own rule and hook holding a payment for approval).

Every step in part 6 is also an automated browser test (studio/test/blackbox/ui-build.test.ts). If a step here stops matching the app, that test fails first.

Use synthetic data only. Never type real names, account numbers, IBANs of real people or other personal data into the studio, its tests, its samples or the AI assistant.

2. Set up and run

The studio is a Node.js server with a web app. It reads its schemas and conformance kit from the specification repository beside it, and keeps everything else, your own work included, as files on a GitHub branch, read into memory. Nothing is kept on disk. Without .NET and Java, everything works except deploying on a real engine; install them when you reach part 7.

Check first: if dotnet --list-sdks lists an SDK starting 8., skip this. You need the SDK, not only the runtime. Install it one of these ways, then open a new terminal.

Your systemCommand

The install script, on macOS or Linux:

curl -sSL https://dot.net/v1/dotnet-install.sh -o dotnet-install.sh
bash dotnet-install.sh --channel 8.0

It installs into $HOME/.dotnet. Add that folder to your path, in your shell profile to keep it:

export DOTNET_ROOT=$HOME/.dotnet; export PATH=$PATH:$HOME/.dotnet

Then check it, and run the conformance kit on DTFx from studio/. The first run builds the DTFx harness, which takes a minute and needs the internet once for its packages.

dotnet --version
npx tsx engines/dtfx/run-kit.ts
dotnet --version starts with 8., and the kit ends 46 of 46 conformance scenarios pass on DTFx. npm run studio -- deploy now works.

The same .NET 8 runs the kit on Elsa Workflows 3, the fourth engine target. Its first run builds the Elsa harness and fetches Elsa's packages:

npx tsx engines/elsa/run-kit.ts
The kit ends 46 of 46 conformance scenarios pass on Elsa. A package exported for the target elsa deploys with the same npm run studio -- deploy command.
If the build fails with error NU1100: Unable to resolve 'Microsoft.Azure.DurableTask.Core', NuGet cannot reach a package source. The harness folder names nuget.org in its own nuget.config, so take the latest code with git pull. If it still fails, your network blocks api.nuget.org: on a company network, ask for your proxy settings or an internal NuGet mirror, and add the mirror with dotnet nuget add source <url> -n company.
On Windows, if the kit or a deploy says An Application Control policy has blocked this file (0x800711C7), Windows is refusing to load the harness the studio just built, because it is not signed. The cause is either Smart App Control (Windows 11, personal PCs) or an App Control or AppLocker policy set by your organisation. Event Viewer, under Applications and Services Logs, Microsoft, Windows, CodeIntegrity, Operational, names the policy. Ways forward:
  • A company PC: ask IT to allow the folders studio\engines\dtfx\harness\bin and studio\engines\elsa\harness\bin, or to give you a developer exception. Do not try to get round the policy.
  • Any PC with WSL: run the studio inside WSL (Ubuntu), where Linux programs are not subject to this policy. Install Node.js and the .NET 8 SDK inside WSL and follow the Linux steps of this guide.
  • A personal Windows 11 PC: in Windows Security, App and browser control, Smart App Control settings, choose Off. It cannot be turned back on without resetting Windows, so decide with care.
Everything else in the studio works without DTFx: the interpreter, the test bench, the kit on the studio and the export.

Start again

Stop npm run studio:dev and start it again: its fake GitHub is in memory, so you start from the seeded content. There is nothing on disk to delete. The factory content and the example bank are seeded from spec/ into content-configurations/, the factory's script-behinds and test samples from studio/scripts/ and studio/fixtures/samples/, and the studio never rewrites a published file. A change set's branch, studio/<id>, is deleted once its change set is on the content branch.

3. The ideas you need

Read this once. Come back to it when a step mentions a word you do not know; the glossary has the short versions.

Tenants, users and maker-checker

One studio serves several banks. Each bank is a tenant. The owner tenant holds shared content: the platform and the schemes. A bank reads shared content and never changes it; it sets its own configuration values and writes hooks. You sign in to the studio, with the studio's own identity provider (for local work and training, the built-in development sign-in lists the users). Everything you do is done as that user, in that user's tenant, and the server checks every change against one permission table. To act as another user, Sign out and sign in as them. The studio's sign-in is separate from the runtime's: a runtime token is never accepted.

UserTenantRoleMay

workflow.designerownerworkflow designerCompose workflows, subflows and schemes from existing blocks, with no code; lands on the workflow designer

Maker-checker. A maker's saves need no approval. A change set becomes a version, the thing that is exported, only when an approver for its area approves it, and the approver is never one of its makers. Every save, approval and refusal goes into a hash-chained audit log.

Names, scopes and releases

Every artefact name is <scope>.<type>.<name>.v<major>, for example uae.p.validate.iban.v1.

ScopeWhat it isExample
pThe platform, the same everywherep.wf.corporate.v1
uae.pThe cluster platform for the UAEuae.p.validate.iban.v1
uae.wpsA scheme, the only one in the factory (provisional)uae.wps.wf.salary-file-out.v1
bA bank's own contentb.hook.pre-release-approval.v1

A release is major.minor.patch. An interface change is a new major, which is a new name (.v2); an improvement is a minor; a fix is a patch. A published release never changes. A change is a new release, and the studio proposes which one from the interface difference.

Values and logic. A value a bank may change (a limit, a list of rails) is a parameter with a default and bounds, looked up by date, so it reaches payments already in flight. Logic is pinned when an instance starts and does not change under it.

How a payment runs

Learn this path. Most of the exercises follow it, and part 6 builds every piece of it.

flowchart LR
  F[File or message] --> D{Dispatch table}
  D -->|start: kind, direction, segment| I[Intake map]
  I --> S[workflow-select]
  S --> P[Platform workflow]
  P --> R[Route: enabled rails]
  R --> L[Scheme leg in the slot]
  L --> X[Post, verify, notify]
  D -->|deliver| A[Workflow that awaits it]
  1. A file or message arrives at the front door.
  2. The scheme's dispatch table says what it is. A start message names the payment it starts (kind, direction and, for an outward payment, segment), its intake map and the leg to start. The dispatch table routes; the intake map only reads the file. Check L33 makes sure every start message leads somewhere real.
  3. The intake map turns the file into the canonical context: header, batch, items.
  4. p.table.workflow-select.v1 picks the platform workflow from the kind, direction and segment. An outward corporate payment runs p.wf.corporate.v1.
  5. The platform workflow validates, screens, checks limits, reserves funds and routes. The route step passes only a rail the bank has enabled in its configuration.
  6. The platform workflow has a slot called scheme-leg. The leg the dispatch table named fills it and does the scheme's part.
  7. Back in the platform workflow: post, verify, notify, with the bank's hooks wherever it bound them.

Composites and the expanded form

A step that talks to a party and waits for an answer calls a composite activity. Underneath, a subflow sends, awaits and reads the reply. The designer sees one step; engines run the expanded form, where each composite step becomes a block of inner steps. A run shows two traces: the business trace, one line per authored step, and the detail, the inner steps.

  • submit:accepted
  • submit.send:accepted
  • submit.await-ack:received
  • submit.read-ack:ack

Runs, benches and the virtual clock

A run happens on a virtual clock that starts on the evaluation date. A wait of days ends at once, and a run is deterministic. A bench binds each port to a simulator and a scenario. A port left out of the bench uses its default simulator, and the run report says so.

Change sets

Some drafts refer to one another: a port and its simulator, a composite and its subflow, a scheme and its legs. None can be published first. Approving a draft therefore publishes its change set, which the studio generates: the draft and every draft it refers to or that refers to it. They are checked and tested together, and all publish or none does. Each change set gets an id such as CS-2026-11-17-001, and an export lists the change sets its artefacts came from.

4. Every feature

A reference to every view in the left menu, then the command line and the HTTP API. Each view lists what it is for, its main controls, and something to try.

Catalogue and artefact pages

Every artefact the tenant can see, published and draft. Search by name, title or data path, and filter by Kind, Scope and Type. Click a name to open its page.

An artefact page shows, as the kind allows: Contract (reads, writes, outcomes, errors), Steps and effective policy, Outline, Rule with its Examples, Gaps and overlaps for a table, Simulator scenarios, Simulators for this port, Message catalogue and dispatch for a scheme, Uses and Used by, Tests that target it, Releases, Provenance, Interface, Issues and the Document itself.

Try. Search iban, open uae.p.validate.iban.v1, and follow Used by to the WPS leg.

AI assistant

Drafts a rule, activity, simulator or script from an instruction and public scheme text, using Claude. Set ANTHROPIC_API_KEY for the studio server to turn it on. Choose a Draft kind, a Target where it applies, and a Language for a script. Then pick a prompt from Start from a template, or write the Instruction yourself, add the Source text, and Ask for a draft.

A template fills the instruction in the studio's own terms, with the parts you must supply in <angle brackets>. Until every one is filled, the page lists them under Still to fill and the request waits. Each template also says what to paste as source text.

KindTemplates
RuleField check; cross-field or batch total; limit with a bank parameter (per payment, per line, per file total); decision

The same templates are served at GET /api/ai/templates, optionally ?kind=rule. What comes back: the Draft, its Questions, the Clauses it relied on, its Provenance and the gate Status. A draft never publishes itself: Save as a draft and follow maker-checker.

The assistant beside every page

Beside the editors, the workflow designer, a bank's configuration and the test bench sits a panel with two tabs. Close it with ×; open it again with the Assistant tab on the right edge.

  • What is happening needs no key. Click into any field and the panel says what it means, the values it takes, an example and the usual mistake. Below that, the document is told in plain words as you build it, with a small picture (for a rule: what it looks at, the condition, the outcome; for an activity: reads, the station, its outcomes; for a workflow: its steps as a story). A checklist shows what is left before it can be published, and the next step. On the bench it tells the last run step by step.
  • Ask is Claude, working beside you. It sees the page, the document as it stands, its checks, the field you are in and the step you selected. Ask a question, or ask it to build: build a rule that checks the days in the pay period are 1 to 31, with tests. It looks around freely (the document, the catalogue, the checks, a bench run). Before it changes anything it asks: Allow once, Allow always (for that kind of change on that page, until you reset it) or Deny. Each change is listed with an Undo; it can undo its own changes too, while the document is still as it left it.

What it may change: the document on the page, a draft saved as you, a test saved as a draft, a sample file. It never publishes: a checker who is not the maker still does that. A document it changed records the model and a reference to its prompt in its provenance. The conversation stays in your browser. Never type personal data.

Import

Brings a scheme in from its source code. An AI coding agent, given the source and the extraction prompt (Download the extraction prompt on the page, or docs/import/EXTRACTION-PROMPT.md), writes an extraction bundle: the studio's own documents, scripts-behind, synthetic samples, tests, a bank's configuration, an inventory of every file and every unit of the source with where each went, and findings (differences between code and spec, questions, error scenarios). The agent checks its bundle with npm run studio -- import <bundle> until it reports no errors.

  • Choose a bundle zip, or Use the training bundle (the factory WPS scheme extracted as uae.wpsx). A platform user imports the shared part; a bank part (scope b, configuration sets) is left for that bank, whose configurator imports it once the shared part is a version.
  • Preview shows what the bundle holds; the coverage of the source (every file inventoried or excluded with a reason; a file in neither is an error); what was retired, sent to infrastructure, or left unmapped for the expert; the findings; every check (schemas, the static checks, no personal data, no bank name in shared content, scripts inside the injected interface, every document explained by the source, a changed published block given a new release); and the bundle's tests, run against the bundle itself before anything is saved.
  • Import as drafts saves everything as drafts (an unchanged block is reused, not saved again), with provenance naming the source and its revision. Nothing is published: an approver approves each change set as a version in Governance. A user who may not author a document of the bundle is refused before anything is saved.

Test bench

Two tabs. Tests lists every test the tenant can see: filter, Run one or Run all. Ad hoc bench runs anything you choose:

  • Start from a test to load one, or choose the Target, Level, Evaluation date and Tenant for the run.
  • Add a port for each binding: port, simulator, scenario. Add a signal for pause, resume, cancel or re-screen at a virtual time.
  • Give the run either Context as JSON or an Inbound sample. Add a sample file saves a new synthetic sample. For a whole payment from the bank's channel, also choose the Start message.
  • Optionally write what you Expect, then Run the bench.

The run report: Checks, Business trace, Detail (Open every composite), Release trace, Timeline on the virtual clock, Instances, Messages in and out, Steps and context deltas, Rule traces, Bench and bindings, and any duplicate or unmatched messages. Save the run as a test turns a run into a test, with the assertions you tick.

The debugger

On the bench, Debug step by step runs the same thing end to end, on the studio's virtual clock, and opens the debugger instead of the report. A saved test has a Debug button beside Run. Nothing it does touches a running payment.

  • Where the run is, on the left: the workflow (and, inside it, the leg or hook it is in), and its steps. A shared segment shows its own steps. Each step is ticked with its outcome as the run reaches it, and the current one is outlined.
  • What happened, on the right, in plain words; then Decisions and rules (the decisions a step took, its findings with reason codes, the rules and tables that ran); Data changed by this event, before and after; and All the data now, with what changed marked.
  • Step into ▶ moves one event forward, into a leg or hook when the run goes there. Step over ⤼ moves on at the same level, past a leg or hook at one go. Step out ⤴ goes back up to the workflow that started this one. Step back and Restart go backwards: a run is the same every time, so stepping back is exact.
  • Click the dot beside a step to set a breakpoint; Continue ⏭ runs to the next one, or to the end. Tick every event to stop on attempts, replies and the rest too. The whole run, event by event lists every stop; click one to jump there. Show the run report gives the usual report.
The debugger keeps the data after every event. For a very large batch it stops keeping it after a limit and says so; debug a smaller sample to see every step.

Conformance kit

The 46 scenarios every engine must reproduce, one per construct of the language: sequence, handlers, switch, parallel, loops, retry, timeouts, awaits, composites, hooks, signals, pins, supersession and more. Run all 46, filter by Construct, or run one and read its expected and actual traces.

Tenant

A bank's own settings, for its Bank Configurator and Bank Approver. A Bank Configurator lands on the Bank workspace: its hooks, rules, dials, simulators, hook bindings, and the test bench for every workflow the bank can configure, run with the bank's configuration. A saved configuration set is a draft until the Bank Approver approves it as a version.

  • Configuration set, Parameters and Hook points: what the bank has set and bound now.
  • Edit the configuration set: the YAML, Bump the release, Reset, and Save the configuration set. Values outside their bounds are refused, and a changed set needs a later release.
  • Parameters this bank may set: every parameter with its default and bounds, and Set a value.
  • Compatibility run: before the bank accepts a new shared release, each bound hook point must still exist with a compatible contract and each of its hook tests must pass.
  • Tenant export: the shared packs the bank accepted, by hash, its bank pack and its configuration set.

Export

Builds the package an engine runs. Tick the Workflows, choose the Target (temporal, dtfx, flowable or elsa) and the Tenant, optionally tick With simulators for a test deployment, then Preview and Download the zip.

The manifest lists: the workers, one per task queue, each with the tasks it serves; the tasks, each named name@release; the flows in expanded form with their pins; the change sets the artefacts came from; and every file with its hash. Flowable packages carry generated BPMN and a portability report. DTFx and Elsa packages are the same but for their binding: both run the documents with one generic interpreter. A package with simulators is marked not promotable. The same request gives the same bytes.

6. Build a full workflow

You will build a new scheme from nothing: its manifest and dispatch table, a port and simulator, maps with a script, a rule, an exchange with its subflow, and a leg that fills the corporate payment workflow's slot. Then you approve it, enable it for a bank, pay a file end to end, and deploy it.

uae.demo is a synthetic scheme made up for training. It stands for no real scheme, and its file format is invented: one H record (file reference, debtor routing code, currency, count, total) and one D record per credit (IBAN, amount).

Sign in as shared.designer until step 8. Each piece is written in the YAML pane of its editor: in the editor, click Start new, then Edit the YAML, replace the text with the document given, click Done, and read the form and the gates. Publishing always means: Request release, then sign in as shared.checker, open Governance, click Approve as version on the draft, and sign in as shared.designer again.

7. Export, deploy and run

An export package is everything an engine needs. The deploy runner starts it on DTFx the way production would run it: a separate worker process per task queue, each serving only its own tasks.

What is in a package

PathWhat it holds
manifest.yamlTarget, workers, tasks, flows, change sets, every file with its hash; whether it is promotable
binding.yamlThe engine binding: one queue per scope, for example uae.wps to th-uae-wps. A new scope gets its queue from the same rule
workflows/, activities/, rules/, ports/, hooks/, schemes/The documents, workflows in expanded form with exact pins
workers/<queue>/One worker: worker.cjs, its manifest.json of tasks, the artefacts and scripts those tasks need, and with simulators, their simulators

bpmn/, portability.jsonGenerated BPMN and the portability report, for Flowable

9. Troubleshooting and reference

When something goes wrong

You seeDo this
A blank page, or a note that the web app is not builtnpm run web:build, then restart
EADDRINUSE on startAnother studio is running: stop it, or set PORT
A publish is refusedRead the message. Usual causes: you are the maker, the user is not a checker, the release is already published, a test is red, or a draft in the change set has an error
L03, a reference does not resolveThe artefact it names is not published and not in your drafts. Check the spelling, or draft it
L22, a port has no simulatorSave the simulator as a draft too; they publish together
L33, a start message routes nowhereIts kind, direction and segment must select a platform workflow whose slot the leg fills
route:no-matchThe tenant's configuration does not enable that rail
hook:hold then hold:declinedThe bank's limit held the payment and operations declined it
No start message in the package's dispatch tablesGive --message for a whole payment, or check the scheme names the leg
dotnet build failed, or dotnet not foundInstall the .NET 8 SDK and open a new terminal; the first deploy builds the DTFx harness. Everything except deploying works without it
An Application Control policy has blocked this fileWindows refuses the unsigned harness. On a company PC ask IT to allow it; or use WSL; on a personal PC, Smart App Control can be turned off. See Install .NET 8
error NU1100 when DTFx buildsNuGet cannot reach a package source. git pull for the harness's nuget.config; check dotnet nuget list source; on a company network, use its proxy or NuGet mirror
java not found, or setup.sh will not runInstall Java 17; on Windows run the setup script from Git Bash
A Python script fails to startCheck python --version shows 3. Or point the studio at your interpreter with TH_PYTHON
The assistant says it has no credentialsSet ANTHROPIC_API_KEY for the studio server
